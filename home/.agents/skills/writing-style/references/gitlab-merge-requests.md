# GitLab merge requests

For GitLab merge requests, write titles in English and descriptions in Russian unless the user requests different languages or the repository requires them. Use the `writing-style` skill. Start descriptions with `Агент:` (or `Agent:` for English), followed by a blank line. Give the title one clear main change. Lead the description with the concrete problem and resulting behavior, then explain how the change solves it and why the relevant choices were made. Write for a reviewer who has not seen the chat. Connect technical detail to behavior, rationale, tradeoffs, compatibility, dependencies, rollout order, or risks. Omit work-session history, inventories of files or implementation pieces, and unrelated scope disclaimers. Use neutral prose to describe the final behavior; rewrite the title and description when scope changes. Keep the main description to one or two short paragraphs, normally no more than about 150 words; a small change often needs only a few sentences. This is a ceiling, not a target. Respect required repository templates and explicit requests for more detail.

Put optional drill-down, such as detailed benchmark methods, large result tables, or extended compatibility evidence, in a closed-by-default `<details>` block with a descriptive `<summary>` label (for example, `Подробности замеров`). Leave blank lines around the Markdown content inside the block and omit the `open` attribute. Use a spoiler only when the extra detail helps review; remove repetition instead of hiding it. Keep the main result, representative measurements with their limits, material risks, rollout dependencies, failed required checks, and readiness limitations visible outside the spoiler.

Do not repeat routine passing tests, lint, coverage, builds, or pipeline status already visible in GitLab CI. Include verification only when it adds evidence the reviewer cannot get from ordinary CI, such as a measured benchmark, manual check, or a particularly informative behavioral regression; state what it demonstrates and its limits briefly, without a check inventory. Disclose failed required checks, known limitations, and missing verification that affects review or readiness. Avoid duplicating MR state from the UI or embedding transient deployment status unless it affects the review. Preserve useful issue and companion-MR links and user-edited content. Preserve uncertainty and conditions when shortening: “may” must not become “does.” Do not invent rationale or infer runtime success from CI.
